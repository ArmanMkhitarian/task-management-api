# PROMPTS

## Подход

Сначала всё обсудил с моделью, потом уже писали код. Сначала 
разобрали стек, архитектуру, спорные места, и только когда всё согласовали, 
пошли в реализацию.

Правила проекта вынес в CLAUDE.md, чтобы модель их держала при генерации. 
Решения с обоснованиями писал в AI_DECISIONS.md, попросил модель фиксировать это, 
план по этапам в PLAN.md.

Делали по этапам, не все разом. После каждого этапа проверял что получилось 
и коммитил. Так удобнее ловить если что-то пошло не туда, и история коммитов 
получается нормальная.

Тесты писал в отдельной сессии специально. Агент который писал код, тестирует 
как бы под себя. А отдельная сессия смотрит на готовый API свежим взглядом.


## Согласование архитектуры

> Строим production-ready REST API микросервис для управления задачами —
> внутренняя система, где команды ведут свои таски. Важна аккуратная
> архитектура и обоснованные технические решения.
>
> Вот требования:
>
> Функциональность:
> - CRUD операции для задач. Свойства задачи: Id, Название, Описание, Статус,
>   Приоритет, Дата/время создания, Дата/время последнего обновления, Email исполнителя
> - Статусы: Новая, В работе, Проверка, Завершена
> - Приоритеты: Низкий, Средний, Высокий, Критический
> - Фильтрация по статусу, приоритету, исполнителю
> - Пагинация списка (limit/offset)
> - Валидация входных данных с понятными сообщениями об ошибках
> - Автоматическая отправка email при назначении задачи (мок, реальные письма не нужны)
> - Health check endpoint с проверкой доступности БД
>
> Технические требования:
> - .NET 6+ с Web API
> - EF Core + БД (SQLite / MySQL / PostgreSQL — на выбор)
> - Документация в Swagger
> - xUnit/NUnit тесты для эндпоинтов (можно не для всех)
> - docker-compose для запуска
>
> Прежде чем писать код, давай разберём подход. Где есть выбор по стеку, необходимо обсудить.
> Также нужно будет обсудить структуру слоев.
> Код пока не пиши — сначала согласуем подход.
